# Typed data access and API contract tooling

Date: 2026-11-08

Scope: a local Node.js + TypeScript application using SQLite. Findings are based only on project-owned documentation, specifications, and repositories.

## Recommendation

1. **Use Kysely + `kysely-codegen` as the MVP SQLite data layer.** This is the closest stable jOOQ-shaped workflow reviewed: introspect the database into types, then use a SQL-shaped fluent API with compile-time table/column/value/result typing. Kysely has a built-in SQLite dialect and migrator. Its main compromise is that codegen is a separately versioned companion and arbitrary raw `sql<T>` result types are asserted rather than checked.
2. **Use Prisma ORM 7 + TypedSQL only if checked `.sql` files outweigh stability and weight.** It is the closest option to jOOQ-style generated functions for named SQL statements, but TypedSQL remains a preview feature, SQLite parameters need manual annotations, generation needs a live database, and the current Prisma 8 line still labels SQLite experimental.
3. **Choose Drizzle instead when one integrated TypeScript schema/migration tool matters more than the jOOQ-like query-builder shape.** Drizzle Kit can pull SQLite into a TypeScript schema and generate/apply SQL migrations, but arbitrary raw SQL types are likewise assertions and the project remains on a fast-moving 0.x/1.0-RC line.
4. **For the API, prefer Connect + Protobuf-ES if RPC-shaped endpoints are acceptable.** It is the only option reviewed that is stable today and cleanly combines one schema, generated TypeScript models/service descriptors, typed Node handlers, browser/Node clients, and genuine discriminated unions (`oneof`).
5. **For conventional REST, TypeSpec is the best model/source language, but run a spike before committing.** Its type system and OpenAPI emitter model discriminated unions well, and it has official JavaScript client and Node/Express server emitters. The server emitter is still explicitly highly experimental, so this path is not yet a low-risk production default. TypeSpec-to-OpenAPI-to-OpenAPI-Generator is mature in shape but fails the strong-union requirement in the specific Node/TypeScript generators.

## 1. Typed SQLite data access

| Option | Schema-first / codegen | Query typing | Migrations and SQLite | Maintenance / risk | Fit |
| --- | --- | --- | --- | --- | --- |
| **Kysely + kysely-codegen** | Kysely requires a `Database` interface and recommends code generation. The separately maintained `kysely-codegen` introspects SQLite into that interface and can verify generated output. | Excellent fluent-query typing: visible tables/columns, joins, aliases, subqueries, and result rows. Raw SQL result types are supplied by the caller as a generic rather than inferred from SQL text. | Built-in SQLite dialect uses `better-sqlite3`; Kysely includes a migrator, but migrations are authored in TypeScript and schema codegen is separate. | Mature, active project; core and codegen have separate release surfaces. | **Best query-builder semantics; less integrated schema workflow.** |
| **Drizzle ORM + Kit** | `drizzle-kit pull --init` introspects SQLite and emits `schema.ts`, relations, metadata, and an initial SQL migration. Kit also generates SQL from a TypeScript schema. | Strong typing for builder queries. Raw `sql<T>` does not infer or validate `T`; the docs say the type is only a helper. | Kit supports generate/migrate/pull/check; ORM supports `node:sqlite`, `better-sqlite3`, and libSQL. | Active releases, but still 0.x and current release notes include breaking changes. | **Best cohesive alternative.** |
| **Prisma ORM 7 + TypedSQL** | `prisma db pull` introspects SQLite into a Prisma schema; Client generation produces a typed model API. TypedSQL compiles named `.sql` files into callable typed functions. | ORM queries are generated and typed. TypedSQL types inputs/results, but SQLite input parameters require `@param` comments; dynamic SQL falls back to untyped/unsafe APIs. | Prisma 7 supports local SQLite and migrations. TypedSQL needs an active database during generation and does not work with the `better-sqlite3` adapter (use libSQL for that path). | TypedSQL is still preview. `npm install prisma` currently selects the Prisma 8 release candidate, whose SQLite package is experimental; using this route means deliberately pinning v7. | **Closest jOOQ-like SQL-file experience, but not the safest default now.** |
| **sqlc TypeScript** | Conceptually the closest SQL compiler: schema SQL plus named query SQL becomes typed functions. | Parses SQL rather than trusting caller-supplied generics. | The official support matrix marks TypeScript as beta for PostgreSQL/MySQL and SQLite as unsupported. It does not solve migrations. | Very early TypeScript plugin; not an MVP choice. | **Revisit when TypeScript + SQLite is supported.** |

### Evidence and caveats

- Drizzle's SQLite database-first guide says `pull --init` generates the TypeScript schema, relations, snapshots, and SQL migration; the Kit overview documents `generate`, `migrate`, `pull`, `check`, and related flows ([SQLite existing database](https://orm.drizzle.team/docs/get-started/sqlite-existing), [Drizzle Kit overview](https://orm.drizzle.team/docs/kit-overview)). SQLite has native Node drivers ([SQLite guide](https://orm.drizzle.team/docs/sqlite/get-started-sqlite)). The raw SQL docs explicitly state that `sql<T>` performs no runtime mapping and cannot dynamically determine the exact type ([`sql` operator](https://orm.drizzle.team/docs/sql)). The official release page shows continuing work and also recent breaking changes, so version pinning matters ([releases](https://github.com/drizzle-team/drizzle-orm/releases)).
- Kysely documents a database interface as the basis of its type safety, recommends production codegen, ships a built-in SQLite dialect, and is primarily a Node.js query builder ([getting started](https://kysely.dev/docs/getting-started), [repository](https://github.com/kysely-org/kysely)). The official raw builder signature accepts a caller-provided result type, demonstrating the boundary around raw-SQL inference ([raw SQL source/API](https://github.com/kysely-org/kysely/blob/master/src/raw-builder/sql.ts)). `kysely-codegen` supports SQLite, emits the `DB` interface, and has a `--verify` mode, but is a separate repository/package ([kysely-codegen](https://github.com/RobinBlomberg/kysely-codegen)). Both repositories show recent releases ([Kysely releases](https://github.com/kysely-org/kysely/releases), [codegen releases](https://github.com/RobinBlomberg/kysely-codegen/releases)).
- Prisma 7 documents SQLite support, introspection, and the normal migration/client workflow ([SQLite](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/sqlite), [introspection](https://docs.prisma.io/docs/orm/prisma-schema/introspection)). TypedSQL generates typed functions from `.sql`, but remains a preview feature; SQLite needs manually declared parameter types, generation requires a live connection, and `@prisma/adapter-better-sqlite3` is excluded ([TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql), [preview status](https://www.prisma.io/docs/orm/v7/reference/preview-features/client-preview-features)). Prisma's current docs say Prisma 8 is a release candidate selected by the unpinned install and its SQLite library is experimental ([ORM overview](https://www.prisma.io/docs/orm), [supported databases](https://www.prisma.io/docs/orm/supported-databases)).
- sqlc's official TypeScript generator demonstrates the desired schema-plus-query-to-functions workflow, but the official language matrix currently marks TypeScript/SQLite unavailable ([TypeScript generator](https://github.com/sqlc-dev/sqlc-gen-typescript), [support matrix](https://docs.sqlc.dev/en/latest/reference/language-support.html)).

### Decision rule

- Pick **Kysely** for the MVP: it is the closest stable match to generated schema types plus a jOOQ-like typed query DSL.
- Pick **Drizzle** if the schema/migration/query workflow must be owned by one TypeScript-oriented toolchain.
- Pick **Prisma 7 TypedSQL** only after a proof-of-concept with the app's hardest reporting query, and pin both CLI and client versions. It is the only reviewed option that actually parses named SQL files into typed functions, but its current stability constraints are material.

No reviewed option provides jOOQ's exact combination of mature SQL DDL introspection, compile-time validation of arbitrary SQLite SQL text, code generation, and migrations in one stable Node package. Kysely is the best stable query-layer fit; Prisma TypedSQL is the best SQL-text fit but is preview; sqlc is the design to watch but does not officially support TypeScript + SQLite.

## 2. One-source API contracts, server handlers, and TypeScript clients

| Option | One source and generated artifacts | Algebraic types | Maturity / limitation | Fit |
| --- | --- | --- | --- | --- |
| **Connect + Protobuf-ES** | `.proto` defines messages and services; generation emits TypeScript messages and service descriptors used by both typed Node handlers and Node/browser clients. Connect runs on Node, Express, Fastify, and browsers and supports Connect, gRPC, and gRPC-Web. | Protobuf `oneof` is a discriminated union; Protobuf-ES represents it as `{ case, value }`, which TypeScript narrows. | Stable and semver-governed. It generates the service contract rather than editable handler stub files; the typed router checks the handwritten implementation. The other tradeoff is RPC endpoint semantics rather than arbitrary resource-oriented REST paths. | **Strongest overall if RPC is acceptable.** |
| **TypeSpec native emitters** | One `.tsp` model can emit OpenAPI, a JavaScript/TypeScript HTTP client, and Node HTTP/Express server scaffolding. | TypeSpec has named unions, `@discriminated`, model discriminators, and `@oneOf`; these are first-class in the source model. | TypeSpec core is active, but docs warn that some client emitters are preview and `@typespec/http-server-js` is highly experimental/alpha. Generated union behavior must be verified with a representative contract. | **Best REST design direction; spike, do not assume production readiness.** |
| **TypeSpec/OpenAPI + OpenAPI Generator** | TypeSpec emits OpenAPI; OpenAPI Generator can create `nodejs-express-server` stubs plus `typescript-fetch` or `typescript-axios` clients. | OpenAPI can express discriminators/`oneOf`, and TypeSpec emits them. However, the generator feature matrices mark union/`oneOf`/`anyOf` unsupported for the Node server and `typescript-fetch`; the Node server also marks polymorphism unsupported. | TypeScript clients are stable, but the Node server is beta and describes itself as alpha; semantic loss at the generator boundary is the key problem. | **Does not meet the strong-union requirement.** |
| **Smithy TypeScript** | One Smithy model can drive TypeScript client and server codegen; generated server code is scaffolding with handwritten business handlers. | Smithy unions are explicitly tagged unions with exactly one set member. | The TypeScript implementation is in Developer Preview, needs the Smithy/JVM build toolchain and a protocol generator, and its quickstart warns about Windows. | **Strong model, but no lower-risk than TypeSpec here.** |

### Evidence and caveats

- Connect's Node guide shows the complete loop: define a Protobuf service, generate TypeScript, implement the generated service on a typed router, and call it from Node or the browser with a generated descriptor ([Node getting started](https://connectrpc.com/docs/node/getting-started/)). Connect-ES declares the project stable, semver-based, and compatible with maintained Node releases ([Connect-ES repository](https://github.com/connectrpc/connect-es)). The Protobuf specification defines `oneof` as a discriminated union ([Buf language specification](https://buf.build/docs/reference/protobuf-language-spec/)); the official Protobuf-ES project generates TypeScript and recommends Connect for typed client/server RPC ([Protobuf-ES repository](https://github.com/bufbuild/protobuf-es)). The generated representation uses a `case` discriminator and `value`, as visible in the project's own discussion of its oneof API ([Protobuf-ES issue 337](https://github.com/bufbuild/protobuf-es/issues/337)).
- TypeSpec supports named unions and network discriminators directly, and its OpenAPI emitter maps discriminated hierarchies plus `@oneOf` unions ([unions](https://typespec.io/docs/language-basics/unions/), [discriminated types](https://typespec.io/docs/standard-library/discriminated-types/), [OpenAPI emitter](https://typespec.io/docs/emitters/openapi3/openapi/)). The official JS client emitter generates HTTP clients ([client emitters](https://typespec.io/docs/emitters/clients/introduction/)); the official server package generates typed service interfaces plus a Node router and optional Express middleware, but labels itself highly experimental ([generated server projects](https://typespec.io/docs/emitters/servers/http-server-js/project/)). TypeSpec itself is actively released ([releases](https://github.com/microsoft/typespec/releases)).
- OpenAPI Generator documents `typescript-fetch` as a stable client but marks Union/`oneOf`/`anyOf` unsupported, while `nodejs-express-server` is beta, calls itself alpha, and marks polymorphism and union constructs unsupported ([TypeScript Fetch](https://openapi-generator.tech/docs/generators/typescript-fetch/), [Node Express server](https://openapi-generator.tech/docs/generators/nodejs-express-server/)). These published feature matrices make this pipeline unsuitable when discriminated unions are a hard requirement, even though it can mechanically produce both sides.
- Smithy's specification defines a union as a tagged union with exactly one member set ([aggregate types](https://smithy.io/2.0/spec/aggregate-types.html)). The TypeScript project provides client and server codegen but explicitly labels itself Developer Preview and notes that applications supply the operation handlers and protocol implementation ([Smithy TypeScript](https://github.com/smithy-lang/smithy-typescript)). Its official quickstart demonstrates a generated client and stubbed server from one model ([quickstart](https://smithy.io/2.0/languages/typescript/quickstart.html)).

### Suggested proof-of-concept gates

Before adopting either API path, model one real sum type, for example a report-import result with `accepted`, `needsProductMapping`, and `rejected` variants, then require:

1. an exhaustive TypeScript `switch` in both client and server code;
2. wire round-trip tests for every variant and for an unknown/future variant;
3. generated handler signatures that prevent returning a response outside the declared operation contract;
4. regeneration in CI with a clean-diff check;
5. a browser call and a Node integration test.

If REST URLs are non-negotiable, spike **TypeSpec's native client/server emitters** first and keep OpenAPI as an emitted compatibility artifact. If stable tooling is more important than REST resource shapes, adopt **Connect + Protobuf-ES**.
