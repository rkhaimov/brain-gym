# 12: Finish the local production workflow

**What to build:** Finish phase one as a dependable local application the creator can start, use entirely offline in Russian, and stop without risking confirmed data. Verify the complete critical workflow and the agreed usability and performance targets.

**Blocked by:** 03: Protect data during startup and migration; 09: Import multi-Outlet Report files; 11: Compare and inspect Outlets.

**Status:** ready-for-agent

- [ ] One documented terminal command starts the production server, waits until startup backup and migration work succeeds, and opens the application in the default supported Chromium browser.
- [ ] Normal terminal shutdown preserves every confirmed change.
- [ ] The server binds only to the local computer and exposes no LAN or internet listener.
- [ ] The production application requires no authentication, external service, or internet connection after it is built.
- [ ] The application emits no external telemetry, usage analytics, diagnostics, or business data.
- [ ] Client, server, and shared TypeScript build reproducibly without OS-specific runtime assumptions.
- [ ] The application targets evergreen Chromium and ships no legacy-browser polyfills or Firefox/WebKit compatibility layer.
- [ ] Every phase-one screen and validation message presented to the creator is Russian.
- [ ] Forms are keyboard-operable, controls are labelled, validation is visible, contrast is readable, and browser zoom remains usable.
- [ ] Final screenshots follow the UI design reference and match the client-approved analytics, Product-mapping, and Report-flow visual direction with only justified functional differences.
- [ ] Generated Protobuf, Connect Query, test, and database artifacts are regenerated by the verification workflow, which fails on an uncommitted generated difference.
- [ ] The critical full-system Vitest flow uses the prebuilt client, real Node.js server, and temporary SQLite database to create Products and Outlets, import and correct a Report file, establish initial Product mappings, and inspect analytics and current Stock.
- [ ] Ordinary views and edits complete within two seconds against the seeded ten-year expected dataset.
- [ ] The maximum expected Report file meets its five-second parse-and-open target in the production build.
- [ ] A documented production-build check confirms LCP at most 2.5 seconds, INP at most 200 milliseconds, and CLS at most 0.1 under the seeded local workload.
- [ ] A manual rebuild and migration preserves existing application data, and the documented recovery procedure successfully restores and migrates an older backup.
- [ ] Coverage reports are published without enforcing an arbitrary global percentage, and every agreed critical scenario is represented at its designated test seam.
